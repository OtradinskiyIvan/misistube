## 1. Общая схема проекта

Архитектура реализована на принципах чистой архитектуры (Clean Architecture) и гексагонального подхода с адаптацией под экосистему Python + FastAPI. Каждый сервис структурирован по слоям, обеспечивающим строгую изоляцию бизнес-логики, внешних зависимостей и транспорта.

```
service_name/
├── src/
│   ├── core/           # Конфигурация, безопасность, логирование, DI
│   ├── domain/         # Сущности, интерфейсы репозиториев, доменные исключения
│   ├── services/       # Оркестрация сценариев, транзакции, бизнес-правила
│   ├── api/            # HTTP-роутеры, Pydantic-схемы, маппинг, валидация
│   └── infrastructure/ # Реализация репозиториев, клиенты БД, S3, очереди
├── tests/
└── pyproject.toml
```

## 2. Ответственность слоёв

| Слой | Назначение | Содержимое | Запрещено |
|------|------------|------------|-----------|
| `core` | Кросс-функциональная инфраструктура | `config.py` (pydantic-settings), `security.py` (JWT, bcrypt/argon2), `logger.py` (JSON-логирование), `di.py`, утилиты | Доменная логика, HTTP-обработчики, ORM-модели, прямые вызовы S3/очередей |
| `domain` | Независимое ядро бизнес-модели | Сущности (`dataclass`), Value Objects, `Protocol` интерфейсы репозиториев, доменные исключения (`UserNotFoundError` и т.п.) | Импорт `fastapi`, `sqlalchemy`, `pydantic`, `boto3`, `core`, `infrastructure`. Любые I/O-операции |
| `services` | Прикладные сценарии (Use Cases) | Классы сервисов (`VideoCreationService`, `AuthService`), управление транзакциями, вызов интерфейсов `domain`, координация внешних портов | Прямая работа с HTTP, ORM, S3. Валидация входных DTO (делается в `api/`). Изменение доменных инвариантов напрямую |
| `api` (presentations) | Транспортный слой | FastAPI `APIRouter`, Pydantic-схемы запросов/ответов, `deps.py` (DI, аутентификация), `error_handlers.py`, маппинг `Domain ↔ DTO` | Бизнес-логика, SQL-запросы, вызов внешних клиентов напрямую. Форматирование ответов вне схем |
| `infrastructure` | Реализация портов | Репозитории (SQLAlchemy 2.0), ORM-модели, клиенты `aiobotocore`/`minio`, обёртки очередей (Arq/Celery), поисковые адаптеры | Доменные правила, HTTP-обработка, конфигурация приложения. Зависимости в обратном направлении |

---

## 3. Правила инверсии зависимостей

1. **Направление импортов:** `api` → `services` → `domain`. `infrastructure` зависит от `domain`. `core` импортируется везде, кроме `domain`.
2. **Контракты объявляются в `domain`, реализуются в `infrastructure`.** Сервисы работают исключительно с `Protocol`, что позволяет заменять СУБД, хранилища или очереди без изменения бизнес-логики.
3. **Запрет обратной связи:** `domain` не должен знать о существовании `services`, `api` или `infrastructure`. При необходимости сложной координации нескольких сущностей используется Domain Service внутри `domain/`, а не прикладной `services/`.
4. **Асинхронность:** Все I/O-операции (БД, S3, очереди, поиск) объявляются `async` на уровне интерфейсов и реализуются асинхронно. Синхронные блокирующие вызовы в цепочке запроса недопустимы.

## 4. Адаптация структуры по сервисам

Полная слоистая структура применяется избирательно, в зависимости от сложности домена и нагрузки на модуль.

| Сервис | Структура | Обоснование |
|--------|-----------|-------------|
| **Creation Service** | Полная: `core / domain / services / api / infrastructure` | Сложная оркестрация, асинхронное транскодирование, управление статусами, интеграция с S3 и очередями |
| **Authorization Service** | Полная или near-full | Критична безопасность, чёткие доменные правила (хеширование, TTL токенов, 2FA), аудит |
| **User Service** | Упрощённая: `core / api / services / infrastructure / models` | CRUD-ориентированный, минимум доменных инвариантов. Валидация и DTO в `api/`, тонкая оркестрация в `services/` |
| **Player & Searching Service** | Адаптированная: `core / api / infrastructure / usecases` | Инфраструктурно-нагруженный (HLS, поиск, кеш). `domain` заменён на DTO и параметры запросов. Бизнес-правила отсутствуют |
| **Interaction Service** | Умеренная: `core / api / services / infrastructure` | Высокая частота записи/чтения, транзакционная, но простая логика. Достаточно изолированных репозиториев и сценариев |
| **Admin Panel** | Минимальная: `api / infrastructure` (переиспользование) | Обёртка над другими сервисами. Не требует собственной доменной модели. |

## 5. Ключевые соглашения разработки

| Аспект | Правило |
|--------|---------|
| **Конфигурация** | Только `pydantic-settings`. Все секреты через `.env`. Разделение по `APP_ENV`. |
| **Внедрение зависимостей** | FastAPI `Depends()` для сессий, сервисов, текущих пользователей. Для сложных графов допускается `dependency-injector`. |
| **Валидация** | Входные данные валидируются строго в `api/` через Pydantic v2. В `services/` передаются уже проверенные типы или доменные объекты. |
| **Обработка ошибок** | Доменные исключения маппятся в `api/error_handlers.py` в стандартный JSON-формат. HTTP-коды соответствуют RFC 7807 или внутреннему стандарту. |
| **Логирование** | Структурный JSON-лог через `structlog` или стандартный `logging`. Обязательный `X-Correlation-ID` для сквозной трассировки через API Gateway. |
| **Тестирование** | `domain` и `services` → unit-тесты с моками репозиториев. `api` → интеграционные через `httpx.AsyncClient`. `infrastructure` → тесты против тестовой БД (Docker/testcontainers). |
| **ORM** | SQLAlchemy 2.0+, `asyncpg` драйвер. Модели изолированы в `infrastructure/database/`. Прямые SQL-запросы допустимы только при доказанной эффективности и инкапсулированы в репозиториях. |

## 6. Контракты и интеграции

- **API Gateway:** Все внешние вызовы проходят через шлюз. Сервисы не общаются напрямую между собой в рамках HTTP. Контракты версионируются (`/api/v1/`).
- **База данных:** Каждый сервис владеет своей схемой таблиц. Кросс-сервисные JOIN запрещены. Данные агрегируются на уровне Gateway или через событийную шину (при необходимости).
- **S3-хранилище:** Доступ строго через `infrastructure/storage/`. Прямая генерация путей фронтенду запрещена. Используются presigned URL для безопасной загрузки/скачивания.
- **Асинхронные задачи:** Транскодирование и индексация выносятся в воркеры. Сервисы лишь ставят задачи в очередь и слушают статусы. Синхронное ожидание завершения тяжёлых операций в HTTP-запросе запрещено.

## 7. Рабочий процесс команды

1. **Ветвление:** Функциональные ветки от `dev`. Слияние через Pull Request с обязательным code review.
2. **Коммиты:** Соглашение Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `chore:`).
3. **Рефакторинг слоёв:** Изменение структуры `domain/` или интерфейсов `Protocol` требует согласования с владельцами затронутых сервисов.
4. **Документация контрактов:** Изменения в API-схемах или DTO сопровождаются обновлением спецификации (OpenAPI/Swagger генерируется автоматически, но breaking changes документируются вручную).
5. **Управление миграциями:** Вопрос внедрения Alembic вынесен на отдельное обсуждение команды. До принятия решения схема инициализируется программно или через ручные скрипты в локальных окружениях.
